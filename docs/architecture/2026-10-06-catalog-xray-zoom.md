# Нозологический каталог, рентген и полноэкранный просмотр

Дата: 06.10.2026. Статус: архитектурная спецификация для будущей реализации.
Этот документ не реализует функции и не разрешает автоматический запуск реализации.

## 1. Основание и границы

Репозиторий: `poberij-crypto/ClinicalPhotoArchive`. Изучена локальная версия
`5721e4deb56d585555e6e352e6ae38cbfc46dbd5`. Через GitHub проверены репозиторий,
main (`7c57357a504dab62a8707f5c1aa9e0b3805888b5`) и открытые PR #1/#2 по
инструментам переноса. При подготовке публикации сравнение коммитов и чтение
изменённых файлов main подтвердили добавление LegacyArchiveImporter и версии
приложения 1.3.0 (versionCode=5). Модель Room, BackupArchive и основной UI
между этими коммитами не изменились. Локальная копия отличается от текущего main; перед
реализацией необходимо сверить описанные ниже файлы с выбранной базовой веткой.
Локальные незавершённые изменения migrator/windows-migrator не являются частью
этой спецификации. Файлы `sources/` не изменяются.

Согласованные требования:

- У пациента ровно один основной нозологический раздел либо «Без категории».
- Пользователь создаёт, переименовывает и удаляет разделы; вложенности нет.
- Рентгенограммы имеют отдельную вкладку «Рентген».
- Полноэкранный просмотр поддерживает pinch-to-zoom, панорамирование и двойное касание.
- Обновление сохраняет пациентов, фотографии и старые резервные копии.

Не входят: облачная синхронизация, отправка медицинских изображений во внешние
сервисы, DICOM/PACS, диагностические измерения, обработка контраста, несколько
нозологических разделов у пациента, массовая переработка архитектуры приложения.

## 3. Модель каталога и инварианты

Новая таблица `categories`, CategoryEntity:

| Поле | Контракт |
|---|---|
| id | Long, PRIMARY KEY AUTOINCREMENT; положительный ID сохранённой записи |
| name | String NOT NULL, отображаемое имя после trim |
| nameKey | String NOT NULL, unique index; нормализованный ключ имени |
| sortOrder | Long NOT NULL; новый раздел получает max+1, первый — 0 |
| createdAt | Long NOT NULL, время создания в миллисекундах Unix |

Нормализация имени: trim, схлопывание последовательностей Unicode whitespace
до одного пробела, NFC, lowercase(Locale.ROOT) для nameKey. Отображаемое имя
также NFC и со схлопнутыми пробелами. Длина 1–100 Unicode code points. Пустое
имя, дубликат nameKey и имя с ключом «без категории» отклоняются. Проверка
unique index обязательна при конкурентных операциях; ошибка выводится в UI.
Порядок пользовательских разделов: sortOrder ASC, id ASC. Ручная сортировка
разделов пока не входит; sortOrder оставляет возможность её добавить позже.

PatientEntity получает `categoryId: Long? = null`, индекс categoryId и FK
categories(id), ON DELETE SET NULL, ON UPDATE NO ACTION. null — единственное
представление «Без категории»; системной строки в categories нет. Раздел
«Без категории» всегда виден первым, включая пустую базу, не удаляется и не
переименовывается. Поле diagnosis сохраняется отдельно и не выводится из имени раздела.

Удаление раздела требует подтверждения с числом пациентов и пояснением перехода
в «Без категории». В одной транзакции обновить categoryId=null и updatedAt
затронутых пациентов, затем удалить раздел; FK служит страховкой. Пациенты,
строки фото и файлы не удаляются. При смене раздела сохраняются все остальные
поля пациента. При переименовании раздела FK и пациентские updatedAt не меняются.
Не использовать REPLACE для categories: его удаление может обнулить связи.

## 4. Границы ответственности и состояния

Сохранить PhotoDao и существующие операции фото. Добавить CategoryDao для
наблюдения разделов со счётчиками (LEFT JOIN, учитывая пустые разделы), вставки,
переименования и удаления. PatientDao получает фильтр по категории с отдельным
условием IS NULL и сохраняет поиск/сортировку по searchKey. Для «Без категории»
считать пациентов отдельным запросом; не смешивать null с режимом «все».

Небольшой CatalogRepository координирует CategoryDao, PatientDao, транзакции,
валидацию и назначение категории; не вводить общий domain/use-case слой ради
четырёх операций. AppViewModel публикует StateFlow каталога, выбранного раздела,
пациента и вкладки. Состояние выбора: CatalogRoot, Uncategorized или
Category(id); nullable ID недостаточен для различения корня и «Без категории».
Команды возвращают понятную ошибку при удалённой категории/пациенте.

Поиск действует внутри выбранного раздела; запрос сохраняется при переходе
между разделами. Смена раздела сбрасывает выбранного пациента и просмотр фото.
При перемещении пациента в другой раздел закрыть его карточку и обновить списки.
При удалении выбранного раздела открыть «Без категории». После восстановления
вернуться в корень, очистить поиск, выбранного пациента и viewer, выбрать BEFORE.

Выбор, запрос, вкладка и открытый photoId сохраняются через SavedStateHandle/
rememberSaveable; после recreation проверить существование ID в текущей базе.
Не сохранять bitmap, Uri доступа или клинический текст в навигационных аргументах.
Формы создания/редактирования должны сохранять незавершённый ввод при повороте.

## 5. Навигация и адаптивный интерфейс

Телефон: Каталог → Раздел → Пациент → Полноэкранное фото. Back из viewer
закрывает viewer, затем карточку, затем список раздела. Создание пациента в
разделе предварительно выбирает этот раздел; создание из корня — «Без категории».
Форма редактирования содержит выбор одного раздела. Диалоги управления разделами
показывают ошибки без потери ввода; повторное нажатие во время сохранения блокируется.

Планшет/раскрытый Fold: использовать уже подключённый Material 3 Adaptive,
учитывать доступное окно и hinge, не только физическую ширину устройства.
Базовый вариант — панель каталога/списка раздела слева и карточка справа;
три одновременные панели не обязательны. В compact режиме последовательная
навигация, в expanded — list/detail. Не размещать кнопки/снимок поверх
разделяющего hinge; tabletop и landscape сохраняют доступность управления.

Перед реализацией этого нового сценария требуется Figma-проектирование по
инструкциям проекта: каталог, список раздела, выбор категории, подтверждение
удаления, карточка с четырьмя вкладками, viewer; compact/expanded и Fold.
Использовать только синтетические записи и изображения. Этот документ определяет
поведение; макеты Figma ещё не созданы и не считаются выполненной проверкой UI.

## 6. Вкладка «Рентген»

Добавить XRAY с dbValue=`xray`, title=`Рентген`, после AFTER. Старые строковые
значения и порядок первых трёх вкладок неизменны. Фото остаются PhotoEntity,
файлы — в filesDir/clinical_images. Новая таблица или каталог файлов не нужны.
Камера, множественный импорт, описание, удаление и fullscreen одинаковы для
всех четырёх разделов. На узком экране вкладки должны помещаться либо прокручиваться.

Цель импорта/камеры фиксируется как patientId + section в момент запуска
операции, а не в момент возврата результата: смена вкладки не должна отправлять
рентгенограмму в «До». Если пациент удалён до завершения, отменить вставку,
удалить только новый несвязанный файл и показать ошибку. При ошибке БД после
копирования также удалить новый файл. При restore блокировать импорт/камеру.
Не менять существующие снимки автоматически на xray по имени файла/диагнозу.

## 7. Масштабирование и панорамирование

Выделить ZoomablePhotoViewer и чистую модель геометрии ZoomState из диалога.
Использовать текущий Compose Foundation; новая production-зависимость не нужна.
ContentScale.Fit, центрированный снимок, начальный масштаб 1x, диапазон 1x–5x.
Двойное касание при 1x увеличивает до 2.5x вокруг точки касания; при масштабе
>1x сбрасывает в 1x и центр. Pinch сохраняет точку под центроидом пальцев;
поворот жестом не поддерживается. Один палец перемещает изображение только >1x.

Пусть fittedW/fittedH — размеры вписанного снимка с учётом EXIF, viewportW/H —
размеры области снимка. Для центрированного transform ограничить offset каждой
оси интервалом ±max(0, (fittedDimension * scale - viewportDimension)/2).
После каждого изменения масштаба/размера ограничивать offset; при 1x offset=0.
Трансформация применяется к снимку, не к кнопкам/описанию; область клиппируется.
Закрытие доступно всегда, системный Back работает. Предусмотреть доступные
кнопки увеличения, уменьшения и сброса для пользователей без multitouch.

На смене фото, повторном открытии и изменении размера окна/повороте сбросить
геометрию в 1x; photoId при recreation сохранять. Bitmap декодировать в IO с
отменой старой загрузки и ограничением памяти, не синхронно в remember.
Отсутствующий/повреждённый файл показывает ошибку с возможностью закрыть viewer.
Не декодировать оригинал заново на каждом жесте. Исходник и EXIF не изменяются.
Текущий sampled bitmap не гарантирует исходную детализацию при 5x; viewer не
является диагностическим инструментом. Tile decoding не входит в этот этап.

## 8. Миграция Room 1 → 2

Версия Room и версия формата ZIP независимы, даже если обе становятся 2.
Нужна явная Migration(1,2), зарегистрированная в databaseBuilder. Запрещены
fallbackToDestructiveMigration и автоматический сброс БД при ошибке.

Последовательность внутри транзакции миграции:

1. Создать categories с указанными типами и unique index nameKey.
2. Создать новую таблицу пациентов с прежними колонками/типами/nullability,
   nullable categoryId и FK SET NULL. Схему точно согласовать с Room JSON v2.
3. Скопировать все поля старых пациентов с теми же ID; categoryId=NULL.
4. Сохранить photos и её FK CASCADE при перестройке patients: снять схему/данные
   фото в промежуточную таблицу, убрать зависимую таблицу photos перед удалением
   старой patients, переименовать новую patients и восстановить photos со всеми
   прежними ID/полями/индексами. Не полагаться на отключение FK внутри транзакции.
5. Создать индекс patients.categoryId, восстановить индексы photos; проверить
   foreign_key_check и итоговые количества. Следующие AUTOINCREMENT ID должны
   быть больше существующих. Room валидирует итоговую схему.

Файлы изображений не перемещаются; localPath остаётся прежним. Все старые
пациенты появляются в «Без категории», categories пустая. Добавление xray
не требует отдельного изменения SQL photos, поскольку section хранится строкой.

До разработки получить schema v1 из неизменённого кода, сохранить в Git
`app/schemas/com.clinicalphotoarchive.data.ClinicalDatabase/1.json`; после
реализации добавить 2.json. При наличии реальной БД v1 сверить схему без
публикации пациентских данных. Ошибка миграции оставляет прежнюю БД доступной
для повторной попытки; UI сообщает о проблеме, не предлагает удалить данные.

## 9. Резервные копии и совместимость

Сохранить ZIP, имя manifest.json, format=`clinical-photo-archive`, images/,
все поля пациентов/фото v1. Новый экспорт всегда version=2, включая пустой
каталог. Дополнения v2: обязательный массив categories (id,name,nameKey,
sortOrder,createdAt); обязательный patient.categoryId (положительный ID или
JSON null); section дополнительно принимает xray. localPath не экспортируется.
«Без категории» не сериализуется как категория. Пустые категории сохраняются.

| Читатель / архив | Поведение |
|---|---|
| Новое приложение / ZIP v1 | Поддерживается; categories=[], все categoryId=null; before/operation/after сохраняются |
| Новое приложение / ZIP v2 | Все категории, связи, четыре типа снимков и байты изображений сохраняются |
| Старое приложение / ZIP v2 | Уже отклоняет version!=1; обратная запись для старого приложения не обещается |
| Новое приложение / неизвестная версия | Отклонить до изменения базы/пользовательских файлов |
| TAR инструментов переноса | Отдельный формат с БД/WAL/SHM; не считать ZIP v1 и не передавать ZIP parser |

Совместимость означает чтение старых копий новой версией. Не маскировать v2 как
v1, не отбрасывать категории/xray ради старого читателя. Снижение версии приложения
с БД v2 не поддерживается; для возврата нужна сохранённая копия v1 и старая версия
приложения в отдельной процедуре. Не объединять это с текущими PR migrator.

Отдельный контракт LegacyArchiveImporter в актуальном main: поддерживать TAR
старой схемы patients/photos без категорий. Новым пациентам назначать null;
при сопоставлении с существующим пациентом сохранять его categoryId и поля.
Импорт остаётся объединением, тогда как ZIP restore остаётся полной заменой.
Проверять исходную SQLite-схему и PRAGMA user_version до импорта. TAR со схемой
Room v2/categories/categoryId или неизвестной схемой отклонять до изменений с
предложением использовать ZIP v2: текущий reader проигнорировал бы эти связи.
Поддержка переноса TAR v2 с отображением ID категорий — отдельное расширение.
Включить legacy import в общую блокировку мутаций и журнал очистки файлов;
не менять эвристику сопоставления пациентов/фото в рамках этого этапа.

Restore сохраняет существующую семантику полной замены, а не слияния. Перед
операцией UI явно подтверждает замену и предлагает экспорт текущих данных.
v1-restore в БД v2 удаляет и прежние категории, затем импортирует пациентов
без категории. Проверка всего архива выполняется до замены:

- Уникальные положительные IDs всех сущностей; ссылки фото → пациент и
  categoryId → категория существуют. Неизвестную ссылку не превращать молча в null.
- Имена категорий соответствуют правилам раздела 3; nameKey сверяется с
  нормализацией name, дубликаты отклоняются; sortOrder неотрицательный Long.
- v1 принимает только before/operation/after; v2 — также xray. Неизвестный
  section отклоняется. Пересчитать searchKey из ФИО/карты, не доверять сохранённому.
- Проверить наличие всех изображений, запретить повторяющиеся ZIP entry names,
  ссылки на один archiveFile несколькими фото и выход за корень распаковки.
  Сохранить ограничение 100 000 entries; потоково ограничить manifest до 16 MiB,
  одно изображение до 512 MiB, суммарную распаковку до 20 GiB. Проверять свободное
  место для staging и новых файлов, фактический предел во время распаковки,
  а не доверять ZipEntry.size. Превышение сообщает об ограничении, не портит базу.

Координатор операций запрещает параллельные restore/export и мутации базы/файлов
до конца архивации; archiveBusy только в UI недостаточен. Экспорт получает
категории/пациентов/фото одним согласованным снимком БД; блокировка мутаций
сохраняет файлы до завершения записи. Не считать частичный ZIP успешной копией.

После полной проверки скопировать фото в уникальные постоянные имена, затем
одной транзакцией удалить photos → patients → categories и вставить
categories → patients → photos. Старые файлы удалять только после commit.
На любой ошибке до commit откатить БД и удалить все новые файлы, включая ошибку
во время копирования (в текущем коде этот путь покрыт не полностью). После commit
ошибка очистки старых файлов не отменяет успешное восстановление; очистку повторить.
Для убийства процесса нужен локальный журнал staging/новых файлов: при запуске
удалять только файлы операции, на которые нет ссылок БД, и завершать очистку
после commit. Не удалять все clinical_images по одному признаку RESTORE_.
Восстановление и экспорт выполняются в IO; сохраняются FLAG_SECURE,
allowBackup=false и отсутствие INTERNET permission.

## 11. Проверки и критерии приёмки

Все fixtures синтетические; реальные пациенты и фото не публикуются.

| Проверка | Ожидаемый результат |
|---|---|
| MigrationTestHelper 1→2: пустая/заполненная база, фото всех трёх разделов, большие IDs | Room schema validation, FK check; все исходные поля, IDs, localPath и counts сохранены; новая вставка без коллизии |
| CategoryDao/Repository: дубликат, кириллица, whitespace, переименование, удаление заполненного раздела | Правила имени, стабильный ID; пациенты переходят в null, фото/файлы сохраняются |
| Назначение/поиск: один пациент, смена категории, пустые категории | Один результат в своём разделе; «Без категории» не исчезает; диагноз сохраняется |
| ZIP v1 → новая база | Старые данные полностью доступны, прежние категории заменены пустым каталогом |
| ZIP v2 round trip | Пустые/заполненные категории, nameKey, порядок, связи, descriptions/timestamps, xray и хеши файлов совпадают |
| Legacy TAR v1 / TAR v2 | v1 добавляет новых пациентов без категории, сохраняет категорию объединённых; v2/неизвестная схема отклоняются без изменений |
| Некорректные ZIP | Unknown version/section, dangling IDs, duplicate names/IDs/paths, traversal, превышение лимитов отклонены; прежняя БД и хеши файлов неизменны |
| Fault injection restore/export | Ошибка копирования, нехватка места, отказ вставки и отмена до commit сохраняют старые данные; после commit/process death восстановление консистентно |
| Конкурентные мутации/камера | Snapshot согласован; импорт остаётся в исходной вкладке/пациенте; удалённый пациент не создаёт orphan file |
| Геометрия zoom | Scale в [1,5]; bounds для portrait/landscape/square; centroid стабилен; double tap 2.5/1; offset=0 при 1x |
| Compose/device UI | Back по уровням, 4 вкладки, формы/выбор после recreation, viewer error, доступные кнопки zoom |
| Fold/планшет/телефон | Compact/expanded, поворот, split-screen, folded/unfolded/tabletop, крупный шрифт; hinge не перекрывает управление |

До выпуска: unit tests и instrumentation (миграция/restore/UI), debug и release
сборки, проверка CI, подписи и permissions. Physical-device сценарии камеры,
SAF backup и Fold не заменяются одним успешным Gradle build.
